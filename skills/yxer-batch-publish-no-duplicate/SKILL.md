# 蚁小二批量发布：防重提交与回执核验

前提：本批稿件、账号范围已得到本人明确批准。本 Skill 只规定怎么安全地提交，不新增任何发布权限。账号范围、分组、挂群等规则以项目规则文件为准，这里不写具体 ID。

## 1. 每批独立执行目录
- 每批建一个执行目录，用 `batch.lock` 文件锁防止同一批并发执行。
- 每次 CLI 调用追加一行到 `commands.jsonl`（时间、命令、参数摘要），stdout、stderr、退出码分别落盘。

## 2. 提交前账号闸门
- 正式提交前（不是审稿时）再跑一次只读 `accounts list` 健康检查，按项目规则逐号核：账号在指定分组内（凭实时分组查询，不按昵称推定）、`status=1`、未锁定或冻结。
- `status` 不是 1 的号直接记 `skipped_unavailable`，不提交、不硬冲，汇报里写明原状态值。
- `status=1` 不等于授权有效，也不等于此前的平台限制已解除，以 `validate` / dry-run 的实时返回和最终回执为准。
- 项目若有发布前预检脚本（频控、本人点头关卡等），每条提交前跑一次，不通过不提交，结果留证。
- 不合格的跳过并记录原因，不提交。

## 3. 三步提交
同一份 payload、同一组通道参数依次跑：
1. `validate`
2. `publish --dry-run`（返回里必须有 `remoteChecks=true`）
3. 正式 `publish`

- 项目要求挂群的，提交前现查一次可挂的群，validate / dry-run 回显里群对象要保留着才往下走。
- 选出的群必须符合项目规则的筛选条件（如名称关键词、当日次数上限）；发现不合规则的，在写入提交意图之前停下改正，不要提交。
- 本人批准时附带了前置条件（如挂群校验必须先通过）的稿件，条件没满足前即使已点批准也先扣住不提交；条件补齐后在同一批准范围内提交，范围外的账号或稿件不顺带加入。
- 校验和正式提交间隔较久时，提交前对同一 payload 再 validate 一次。

## 4. 意图与回执
- 正式提交前用排他创建（O_EXCL）写 `submit_intent.json`：批准标识、payload 的 sha256、账号、时间。文件已存在就说明提交过或正在提交，停下核对。
- 拿到 `taskSetId` 后写 `submitted.json`。

## 5. 断点续跑
先看本地记录再动：
- 已有回执：只轮询 `query details`，不再提交。
- 有 intent 无回执：结果未知，只读核对（查近期发布记录有没有同题），默认禁止重投；唯一例外见第 6 节「发出前失败」。
- 无 intent：intent 之前的失败（如健康检查超时），可等服务恢复、查 records 确认无同题记录后补投一次。

## 6. 出错处理
- 只有 stdout 里是 JSON 且 `ok:true` 才算调用成功；HTML、空输出、非 JSON 一律不算。
- 传输错误（EOF、TLS、超时、502–504）按出错阶段分开处理：
  - 写 intent 之前、不会产生发布的步骤（只读查询、validate、dry-run、素材上传、填表绑账号、归档读回）：同一步骤可按 30s、60s、120s 间隔最多重试 3 次，每次照样落盘；重试成功就照常往下走。
  - 重试 3 次仍失败，或多个账号连续出错：写 `GLOBAL_STOP`，整批停下，不继续后续账号。隔几分钟只读健康检查，恢复后先查 records，确认已成功的不重投、其余无同题记录，再从断点续跑。
  - 写了 intent 之后才出现传输错误：标 `unknown_submit_DO_NOT_RETRY`，只读核对。正式 `publish` 默认只发一次，不算在上面的重试里。
- 发出前失败（intent 之后唯一可补投的情况）：CLI 的错误详情明确写着失败发生在它发出发布请求之前的只读查询上（例如读取平台账号列表的 GET 握手超时），并且隔几分钟分多次查 records 都没有同题记录，才可补投，且只补 1 次：
  - 先把原 intent 和诊断文件整体移到 `unknown_<时间>_attempt<N>/` 留证目录，再重新排他写 intent。
  - 补投前照常 validate / dry-run。
  - 补投仍失败：写 `STOP_DO_NOT_RETRY.json`（`not_submitted_retry_exhausted`，附两次诊断和 records 核对），不再重试，交上级决定。
  - 看不出失败点、错误发生在发布请求之后、或 records 有同题或查不到：一律按结果未知处理，不补投。
- 单个账号被平台拒：只隔离这个号，其他号照常。
- 平台以「违反社区规范」等内容/账号原因拒发：标 `failed_isolated_no_retry`，不自动重试、不改稿重投、不去掉挂群等必需项硬冲（这类失败不是群被拒）；失败源素材不按成功归档。
- 同一账号换了新图新题新文案后再次因同类原因被拒，按账号层面受限处理：汇报里单独标出，建议后续批次是否暂停该号由本人决定，不自行继续排稿给它，也不自行把它移出范围。

## 7. 结果判定
- `query details` 里 `stageStatus=success` 且 stage 为 push 或 success 才算发布成功。
- fail 的隔离并报告，不自动重试。
- `publishId`、`openUrl` 有就记，没有就写没有，不自己拼链接。
- 挂群等附加项：提交成功但 details 里没有对应字段时，只能报「已在载荷提交、前台未确认」，需本人在 App 里核实，不能说已挂。
- 刚发出的小红书笔记，匿名打开网页端常被拦成「暂时无法浏览」，看不到挂群信息；不要靠匿名网页、登录态或 cookie 去绕，直接按「前台未确认」报告。

## 8. 收尾
- 每个入口跑完写 completion 标记（run_id、退出码、错误），作为交付依据。
- 汇报逐账号列：成功 / 失败隔离 / 跳过不可用 / 结果未知 / 发出前失败已停，附 taskSetId 和查到的链接；结果未知的说明下一步只读核对。中途重试或补投过的步骤也写明，说明没有因此重复提交同一稿件。
